```text
              ├─ MediaCrawler：抖音增量

              └─ 可选流水线：下载 → 转写 → 抽帧 → 待 AI 笔记
```

组件职责不可混淆：

- 前端只负责展示、管理博主/分组/标签和调用 API。
- 聚合 API 是本地数据、认证、接口和媒体预览出口，不负责持续轮询。
- 监控层负责心跳、按平台周期轮询、去重入库和消费网页触发器。
- RSSHub 是 B 站、推特 X 的抓取依赖；它不是前端或聚合 API 的一部分。
- 下载、转写、抽帧和 AI 笔记是可选流水线。当前关闭，不会因轮询自动执行。

## 7. 从发现到笔记的工作流

### 7.1 仅监控模式

1. 监控层按周期读取所有 `enabled=1` 的博主。
2. 平台适配器返回作品元数据：平台、外部 ID、标题、原文 URL、发布时间、类型、封面等。
3. `UNIQUE(platform, external_id)` 与现有作品比对，新增作品写入 `works`，状态为 `QUEUED`。
4. 更新 `creators.last_poll_at`、`last_work_at`、cookie 健康度及 `poll_logs`。
5. 因 `MONITOR_RUN_PIPELINE=false`，新作品停留在 `QUEUED`，不下载任何媒体。

网页“立即爬取”走 `POST /api/v1/monitor/poll-now`。它调用 `monitor/onetime_poll.py`，RSSHub 不存在时临时启动，抓取结束后仅关闭本次拉起的 RSSHub；若 RSSHub 已常驻，则不会关闭它。

### 7.2 可选流水线模式

将 `MONITOR_RUN_PIPELINE=true` 后，监控层每 30 秒最多处理 10 条 `NEW/QUEUED` 作品：

```text
QUEUED
  → DOWNLOADING
  → TRANSCRIBING
  → FRAME_EXTRACTING
  → NOTE_GENERATING
  → 等待 WorkBuddy / 人工生成笔记
```

- 视频：按平台下载 → FunASR paraformer 转写 → 词库命中的语义抽帧；词库无命中时均匀抽帧兜底。
- 图文：下载图片，写 `frame_manifest.json`，跳过语音转写和视频抽帧。
- 失败：作品标记 `FAILED`，错误写入 `last_error` 和任务表，可通过 `POST /api/v1/works/{id}/retry` 重新排队。
- AI 笔记：`notify_ready` 生成 WorkBuddy 待处理信息；API 的 `analyze` 操作写出待分析清单。当前代码没有内嵌云模型调用，最终笔记由 WorkBuddy / 人工处理后回填到 Obsidian 和 `note_path`。

## 8. 数据模型与文件布局

### 8.1 SQLite 表

| 表 | 关键字段 / 职责 |
|---|---|
| `creators` | 平台、外部 ID、主页、启用状态、分组、最近轮询和最新作品时间；`platform + external_id` 唯一 |
| `works` | 作品元数据、状态、媒体/转写/抽帧/笔记相对路径、内容类型、封面、失败原因 |

| `lexicon` | 语义抽帧词条、权重、正负向动作与分类 |
| `cookies` | 仅存凭据健康状态，不存 cookie 明文 |
| `poll_logs` | 平台轮询开始/结束、状态、异常类型、新增作品数 |

启动时 `init_db()` 会建表并进行幂等轻量迁移：补齐 `works.content_type`、`media_urls`、`cover_url`，`lexicon.category` 和 `poll_logs.new_works`。

### 8.2 媒体和知识库布局

```text
media/{分组}/{博主}/{日期}-{标题}/
  ├─ 视频或图片
  ├─ transcript/

  └─ images/
```

## 9. 聚合 API

除 `GET /api/v1/healthz` 外，所有 API 均需 `Authorization: Bearer <ADMIN_TOKEN>`。响应采用统一外层：`code`、`data`、`message`。接口总数为 31 个（含健康探针）。

| 资源 | 接口与用途 |
|---|---|
| 健康 | `GET /healthz`；`GET /health/cookie`；`GET /health/system` |
| 博主 | `GET/POST /creators`；`GET/PATCH/DELETE /creators/{id}`；`GET /creators/{id}/works` |
| 作品 | `GET /works`（平台、状态、关键词、标签、分组、博主等过滤）；详情；本地视图；重试；分析；归类；关键帧 |
| 分组 | `GET/POST /groups`；`PATCH/DELETE /groups/{id}` |
| 标签 | `GET /tags`；`GET /tags/{name}/works` |
| 词库 | `GET/POST /lexicon`；`PATCH/DELETE /lexicon/{id}` |
| 监控 | `POST /monitor/poll` 写触发器；`POST /monitor/poll-now` 启动一次性爬取；`GET /monitor/poll-status` 返回最近轮询 |
| 待分类 | `GET /unclassified` |
| 微信 | `POST /wechat/import`，当前明确返回 501，属于预留接口 |

OpenAPI 页面可在本机 `/docs` 查看。后续改动应同步更新 `docs/openapi-aggregator.yaml`；现有 README 所称“27 个端点”已落后于源码实际数量。

## 11. 启动、停止与日常操作

### 11.1 当前已验证的启动组合

```text
后端：  backend 中启动 uvicorn，监听 127.0.0.1:8001
前端：  frontend 中启动 Vite，监听 127.0.0.1:5180
RSSHub： tools/rsshub 中运行 dist/index.mjs，监听 1200
监控：  项目根运行 monitor/main.py
```

启动顺序建议为：RSSHub → 后端 → 前端 → 监控层。停止时先停止监控层，再停止 RSSHub、后端和前端，防止轮询写入被中途截断。

`start_all.bat` 与 `stop_all.bat` 是历史的一键脚本，但当前脚本对 RSSHub 的常驻启动覆盖不足，且文档中的端口示例已陈旧。使用脚本前应先检查其端口与本机 Node/Python 路径是否和当前 `.env` 一致。

### 11.2 常用运行判断

- 前端报“无法连接聚合 API”：先检查后端 8001、前端 CORS 是否包含 5180、前端 API 基地址是否为 8001。
- 仪表盘 RSSHub 显示离线但 `http://127.0.0.1:1200/healthz` 正常：当前健康服务仍探测 `/health`，而现行 RSSHub 健康端点为 `/healthz`，属展示检查不匹配。
- 监控层显示离线：检查 `workbuddy/monitor_heartbeat.json` 的更新时间和 `monitor/main.py` 进程。
- 新作品不下载：先检查 `MONITOR_RUN_PIPELINE`；当前关闭是正常预期。
- B 站定期出现一次 `network` 失败：当前数据库存在一条 B 站链路验证测试博主，非真实目标的无效外部 ID 会导致该失败日志。

# 链接直达本地分析 Skill：设计规格

日期：2026-09-19  
状态：已获功能设计确认，待实现计划审核

## 1. 目标与边界

用户在对话中先发送一条作品链接。Codex 随后自动识别抖音、B 站、小红书或 Twitter/X，完成该作品的本地下载、转写、关键帧和 AI 笔记，并将全过程与结果展示在现有网页的作品列表/详情/本地视图中。

默认模式是**一次性分析**：作品以 `source_type=manual` 入库，不创建博主、不加入持续监测。仅当用户明确表达“加入监控”“持续监测”“关注该博主”等意图时，才进入监测模式。

这项能力取代该链路中 WorkBuddy 的“笔记待处理”角色：Codex 在当前对话执行期间直接生成并保存 Obsidian 笔记。它不是无人值守的后台大模型服务；会话不在运行时，监测到的新作品仍只进入既有队列。

不在范围内：清空或迁移现有项目/数据库、自动处理全部积压 `QUEUED` 作品、启用 `MONITOR_RUN_PIPELINE`、导出或展示任何平台 Cookie、把“用户仅发链接”误解为“加入监控”。

## 2. 已确认的交互契约

1. 用户直接发送链接；不得在收到链接前要求选择平台或分析方式。
2. Skill 按域名及作品 ID 识别平台；只有平台无法判定、链接不完整或不受支持时，才只问一个平台问题。
3. 无明确监测用语时，默认一次性分析并立即在前端可见。
4. 有明确监测用语时，先分析该作品，再创建或启用对应博主；若作品链接无法可靠得出博主主页与平台外部 ID，才追问该博主主页链接，不猜测身份。
5. 下载、转写、关键帧和笔记都落在 `F:\媒体监测`；下载任务只针对本次 `work_id`，不触发全局队列。

## 3. 方案选择

采用“API 入库 + 单作品本地执行器 + Codex 完成笔记”的方案。

- 不让 Skill 直接修改 SQLite：所有作品/任务/笔记完成状态通过聚合 API，保持鉴权、幂等、前端契约和测试边界。
- 不开启常驻队列：新增的执行器只接收一个 `work_id`，复用 `monitor.jobs` 已有下载、转写、抽帧实现。
- 不再依赖 `workbuddy/pending` 来请求笔记：执行器只标记“素材已就绪”；Codex 读取本地产物，直接写 Obsidian 笔记，再调用笔记完成接口。

## 4. 新增接口契约

### 4.1 `POST /api/v1/link-analyses`

受现有管理员认证保护。请求包含：

```json
{
  "url": "https://...",
  "platform": "bilibili",
  "external_id": "BV...",
  "mode": "one_time"
}
```

- `platform` 与 `external_id` 由 Skill 的链接识别步骤提供；后端再次校验平台与 ID 格式。
- `mode` 只允许 `one_time` 和 `monitor`。Skill 未见明确监测意图时固定传 `one_time`。
- 对相同 `(platform, external_id)` 幂等：返回既有作品和 `created=false`，绝不复制下载/笔记目录。
- 新作品创建为 `source_type=manual`、`status=QUEUED`，并写 `parse`、`download`、`transcribe`、`frames`、`note` 的待处理阶段。初始标题可为“待解析 {external_id}”，在下载完成后由可获得的元数据/文件名回填。
- 返回 `work`、`created`、`mode`。前端无需新页面：现有作品列表已经展示 `manual=手动`，详情与本地视图会随状态更新。

`mode=monitor` 仅表示调用方已明确意图；创建/启用博主的动作仍需要可信的作者资料。服务返回 `creator_resolution_required=true` 时，Skill 只向用户索取作者主页链接，已创建的单作品不丢失。

### 4.2 `POST /api/v1/works/{work_id}/complete-note`

仅接受位于 `OBSIDIAN_ROOT` 内的相对 `note_path`。服务验证文件存在且扩展名为 `.md`，再原子地：

- 回填 `works.note_path`；
- 将 `works.status` 设为 `DONE`；
- 将 `note` 阶段设为 `succeeded`；
- 清除旧的笔记阶段错误。

拒绝绝对路径、`..` 路径逃逸、缺失文件及非 Markdown 文件。重复提交同一路径成功且幂等。

## 5. 单作品执行器

新增项目脚本/服务入口（实现名称在计划阶段确定），例如：

```text
python tools/process_link_analysis.py --work-id 123
```

其职责是按该 ID 加载一条 `QUEUED` 或可重试作品，并调用已有的 `_process_work` 分支：

```text
下载 → 转写 → 词库匹配/兜底抽帧 → 素材已就绪
```

它必须：

- 在每个阶段开始时写 `running`，成功时写 `succeeded`，失败时写该阶段 `failed` 和可读 `last_error`；
- 不扫描、处理或改变其他作品；
- 不依赖 `MONITOR_RUN_PIPELINE=true` 或监控层常驻；
- 对已完成素材幂等复用，避免失败重试覆盖已有本地文件；
- 在最后不调用 `notify_ready`/不创建新的 WorkBuddy pending 清单，而把笔记阶段保持 `pending`，由 Codex 接手。

原有监控流水线保持兼容：它仍可按当前配置创建 WorkBuddy pending 清单；本功能只改变手动链接的处理路径。

## 6. Codex Skill 行为

Skill 放入用户级可发现目录，名称暂定 `local-media-link-analysis`。触发条件是用户提供一个四平台作品链接并要求下载、转写、总结、笔记或分析；不应用于纯浏览/评论抓取请求。

执行顺序：

1. 从链接识别平台；短链先只解析 HTTP 跳转到规范链接，不能解析则询问平台。
2. 从文字上下文判断模式：显式监测词为 `monitor`，其余为 `one_time`。
3. 调用入库接口，报告网页中可打开的作品 ID/链接；已存在则说明会复用，而不是重复下载。
4. 调用单作品执行器，监看本次阶段；失败时停止，不伪造转写或笔记，并把失败原因回报用户。
5. 读取该作品的转写稿、关键帧清单、原始链接和本地文件，创建结构化 Obsidian Markdown 笔记。
6. 调用 `complete-note` 回填状态，再读取作品详情确认网页可见的 `note_path=...` 和 `status=DONE`。
7. `monitor` 模式在作者资料可靠时创建/启用博主；不自动下载该博主历史作品。

笔记至少包含来源链接、平台、下载时间、本地素材位置、转写摘要、关键观点/时间点、关键帧引用和不确定性说明。内容只能基于本地转写、关键帧和来源元数据，不能捏造未见内容。

## 7. 平台能力与失败策略

| 平台 | 当前下载链路 | 处理原则 |
| --- | --- | --- |
| 抖音 | jiji262，最低可转写画质为 480p | 环境或作品限制失败则保留失败状态 |
| B 站 | yutto，360p | 支持单视频链接；登录受限内容使用本机现有授权环境 |
| 小红书 | XHS-Downloader，需要项目现有 Cookie | 不展示 Cookie；图文作品应走图文分支，不能强行转写 |
| Twitter/X | yt-dlp，通常需要代理，Cookie 可选但常必要 | 视频按现有下载器；纯图文使用既有图文下载分支，不声称有音频转写 |

所有短链接、私密/登录受限内容、反爬拦截、下载器缺失、无音轨媒体和转写引擎失败都应形成可重试的 `FAILED` 记录，并保留已成功阶段的产物。

## 8. 前端呈现

不新增独立的“一次性分析”页面。因为新作品以 `manual` 来源写入现有 `works` 数据，现有页面即可展示：

- 列表中的“手动”来源和当前状态；
- 详情的下载/转写/关键帧/笔记阶段；
- 本地视图中的文件清单与笔记全文；
- 笔记完成后的 `DONE` 状态及 Obsidian 打开入口。

实现时仅在现有筛选页确认 `source_type=manual` 可被发现；若无现成筛选入口，增加轻量的“手动分析”筛选，不改变导航结构。

## 9. 测试与验收

后端先写失败测试，再实现：

1. 合法 B 站链接创建 `manual/QUEUED` 作品和全部待处理阶段；重复链接只返回原作品。
2. 未知平台、平台与 ID 不匹配、非法 `mode` 返回 422。
3. 单作品执行器只选择传入 `work_id`，在 `MONITOR_RUN_PIPELINE=false` 时仍能运行；失败只影响该作品。
4. 允许的笔记路径完成后变为 `DONE`，路径逃逸/不存在笔记被拒绝。
5. 既有 `/works`、重试、监控轮询与 WorkBuddy pending 测试继续通过。

验收以一个可公开访问、含音轨的测试作品为准：前端出现“手动”作品 → 本地媒体与转写文件存在 → 关键帧清单存在 → Obsidian 笔记存在 → API 与网页显示 `DONE`。真实用户链接只在用户本次明确提交时处理。

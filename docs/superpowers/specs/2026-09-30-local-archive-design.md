# 下载作品信息与本地归档统一设计

日期：2026-09-30  
状态：设计已获用户确认；本文是设计规格，功能尚未实现。  
目标仓库：`c2586081610-sys/social-monitor-workbench`  

## 1. 用户目的与已确认选择

让项目在每次下载时自动记录平台、原作品链接、发布时间和下载完成时间，自动整理目录及生成单作品信息 CSV、合集清单，并在网页中查看。规则作为项目功能和文档长期保留，后续运行无需重复提出这些要求。

用户已确认：

- 历史作品补齐信息与 CSV，保留已有目录、文件名和媒体位置。
- 新作品文件夹使用发布时间；CSV 和网页同时包含发布时间与下载完成时间。
- 增加“本地归档”页面，统一查看历史及新下载作品，支持平台和时间筛选、CSV 导出。
- 完成融合后推送到用户现有 GitHub 仓库。

新下载覆盖项目已有的 B 站、抖音、小红书、Twitter/X 下载入口。归档筛选和导出兼容项目现有平台枚举（前端类型还包含 `wechat`）；每个平台只使用实际可用的元数据来源，无法核实时保持未知，不因枚举存在就宣称平台查询能力已实现。历史回填首先处理用户指定的谭成义 B 站母库及既有合集；其他历史目录使用同一归档入口按需纳入。

## 2. 当前证据

- `Work` 已有 `platform`、`external_id`、`url`、`published_at`，没有独立下载完成时间。
- `monitor/jobs.py` 使用 `media/{分组}/{博主}/{日期}-{标题}`，缺少目录中的平台和作品 ID。
- 现有 `作品信息.md` 仅写作品链接和数据库更新时间，无法区分发布、下载、信息编辑。
- 手动链接入库可能仍是“待解析 ID”，发布时间为空；需要在分配新目录前尝试获取作品详情。
- 网页列表已显示平台和发布时间；缺少下载时间、归档核对状态和 CSV 导出。
- 原始素材母库 `健身` 与项目生成目录 `media` 并存，后端本地视图当前主要服务 `media`。
- 指定母库有 175 个作品文件夹；现有总表有 177 条媒体文件记录，其中 63 条同时具备作品 ID 与发布时间，114 条仍缺少这些信息。条目数与文件夹数不能直接视为作品数。
- 现有单作品和合集 CSV 表头不同，应兼容读取后统一输出；已有合集保留其选定作品范围。
- 工作区存在其他未提交的代码、媒体与运行数据，发布本功能需要精确选择提交范围。

## 3. 方案比较与选择

1. **统一归档索引与自动生成文件（选择）**：数据库索引负责网页筛选、导出与同步状态；单作品 CSV/JSON/Markdown 与合集 CSV 来自同一个归档记录。支持历史目录及流水线入口，能够补写与重试。
2. **只写下载后处理脚本**：改动较少，但网页、手动入口、历史清单仍容易出现不同规则。
3. **网页每次扫描整个媒体盘**：无需索引表，但响应时间随素材增长，不能稳定维护核对状态和同步失败记录。

选择方案 1，在原项目内增加归档服务，复用现有 FastAPI、SQLAlchemy、SQLite、React 和 Vite，不另起项目。

## 4. 时间与来源的明确含义

| 信息 | 定义 | 缺失时的行为 |
|---|---|---|
| 发布时间 `published_at` | 原平台公开发布的时间 | 保持空值，展示“发布时间待核实” |
| 下载完成时间 `downloaded_at` | 最近一次确实写入并验证媒体成功的完成时间 | 历史无可信证据时保持空值，展示“下载时间未知” |
| 信息核对时间 `metadata_checked_at` | 最近一次成功查询或人工核对信息的时间 | 单独记录，不能代替发布或下载时间 |
| 信息更新时间 | 归档信息或索引编辑时间 | 用于同步判断，不能代替其他时间 |

- 数据库存 UTC ISO 8601；网页、CSV 与目录按 `Asia/Shanghai` 展示，并明确标注北京时间。
- 时间来源、核对状态及时间精度与时间一起保存。已有 CSV 只有分钟精度时不能宣称其秒数已核实。
- 文件创建时间、修改时间、视频文件名中的拍摄日期仅能作为辅助线索，不能自动填入真实发布时间或下载完成时间。
- 同一媒体复用、跳过下载或仅重试转写时，不修改下载完成时间；真实重新下载成功时更新该时间。失败及零字节文件不会产生成功时间。
- 图文仅在所需媒体实际下载成功后记录下载完成时间。纯文本归档保留“无需媒体下载”，不伪造下载行为。

## 5. 新作品目录规则

```text
media/
  分组/
    博主/
      发布时间_平台_标题_作品ID/
        原媒体文件
        作品信息.csv
        作品信息.json
        作品信息.md
        transcript/
        frames/
        images/
      合集清单.csv
  归档总清单.csv
```

格式示例：`健身/谭成义/2026-08-31_18-49_哔哩哔哩_训练日的一天_BV1F9t86dEK2/`。此例用于说明格式，历史目录不会据此更名。

- 平台显示名统一为“哔哩哔哩”“抖音”“小红书”“Twitter/X”；目录清洗后的名字使用“X”，代码保留平台枚举。
- 日期至少明确到已经核实的精度；缺失时使用“发布时间未知”，不会使用入库日期代替。
- 标题清洗非法字符、Windows 保留名及尾部空白，并按完整路径预算截断；作品 ID 必须保留，避免同名作品覆盖。
- 分配目录前先尝试解析作品详情。已经分配或已经存在的媒体路径在重试及信息补齐后保持稳定。
- 博主与分组名称来自现有模型；未分组或无博主时采用明确的默认名称。同名博主冲突用稳定身份后缀区分。
- 合集是作品清单及本地引用，默认不复制媒体，不把视频拼接成新视频。

## 6. 自动保存的作品信息与 CSV

单作品 `作品信息.csv` 与标准合集 CSV 使用相同基础列：

```text
归档ID,作品标题,平台,平台代码,博主,分组,作品ID,平台链接,
发布时间（北京时间）,发布时间精度,下载完成时间（北京时间）,
发布时间来源,下载时间来源,信息核对状态,信息核对时间（北京时间）,
本地根目录标识,本地作品目录,本地媒体文件,媒体数量,媒体大小（字节）,备注
```

- CSV 为 UTF-8 BOM，便于 Windows Excel 直接打开中文；使用标准 CSV 转义处理逗号、引号和换行。
- 对标题等不可信文本进行 Excel 公式注入防护，JSON 保留原始文本。
- 单作品以一条作品记录表达多个媒体文件，JSON 保存明确的文件数组；合集同样按归档作品记录聚合。
- 历史 `BVID`、`本地媒体路径` 等旧字段兼容读取。已有总表/合集升级时保留额外用户列，并新增统一字段，不丢弃原有值。
- 既有按媒体文件逐行记录的历史 CSV 保持原来的行粒度；新的标准作品 CSV 按作品聚合，不能为了统一格式删除原有媒体文件行。
- `作品信息.json` 带 `schema_version`，为程序读取提供无损信息；`作品信息.md` 保留现有可阅读信息入口。
- 三种信息文件由同一记录生成，不能各自推算不同的平台或时间。
- 每个博主目录的 `合集清单.csv` 在归档更新后自动重建；`media/归档总清单.csv` 汇总已纳入索引的全部本地作品。
- 原有 `全部作品信息.csv` 继续保留并补齐字段。原有指定合集只更新原来选定作品的信息，不扩大为整个母库。
- 用户导出的筛选合集包含全部符合条件的记录，不能只导出网页当前页。

## 7. 数据与服务边界

### 7.1 在现有 Work 中增加下载信息

新增可空的 `downloaded_at`、`download_time_source`，API 增加对应信息和关联归档状态。迁移沿用项目幂等加列方式，兼容已有数据库和已有 API 消费者。

### 7.2 增加本地归档索引

新增 `archive_entries`，主要包括：

- 主键 `id`；唯一定位键 `(root_key, relative_directory)`。
- 可空 `work_id`，关联已有流水线作品；历史作品可以仅有归档记录。
- 平台、可空作品 ID、博主、分组、标题，用于筛选及匹配。
- 发布与下载时间、来源、精度、核对状态、核对时间。
- 版本化的完整元数据和媒体文件清单。
- 元数据修订历史，记录人工修改前后值、时间及来源。
- 同步状态 `pending/ready/failed`、最近同步时间、错误说明。

历史归档不必创建可运行的 `NEW/QUEUED` 作品，不会因扫描母库触发自动重下载。识别到同一平台与作品 ID 的现有 Work 时，建立关联；不能凭相似标题覆盖其他 Work。

同一作品在不同真实目录有多个副本时保留多个物理归档记录；关联同一个作品身份。一个目录含多个不同作品时报告冲突，不能自动合并身份。

另设独立的 `archive_jobs` 持久保存扫描/补齐任务的状态、允许根与子目录、进度游标、统计和错误。由归档工作器消费，与现有依赖 Work 的媒体阶段任务分开；服务中断后可从游标恢复，进度无需依赖内存状态。

### 7.3 限定可索引目录

- 项目生成媒体根默认为现有 `MEDIA_ROOT`，根标识 `media`。
- 历史素材根默认为项目 `健身`，根标识 `fitness`；通过本机配置声明其他历史根。
- API 使用根标识和相对目录，不接收任意绝对磁盘路径；解析路径及联接后校验仍在允许根内。
- 本地历史文件按受认证的归档记录提供访问，不把整个 F 盘或整个 `健身` 目录直接公开挂载。
- 根目录映射、本机索引及媒体清单属于本机数据，不写入 GitHub。版本化默认归档规则属于源码与公开文档。

## 8. 信息解析与核对

统一元数据解析接口，供手动链接、监控作品、历史补齐和网页刷新调用。

优先顺序：已有可信平台数据 → 指定作品详情查询 → 下载器提供的可信作品元数据 → 人工核对。持久保存每个结果的来源和核对时间。

- 已有四平台监控数据都按统一结构接入；B 站历史信息补齐首先正式化现有查询能力。
- 手动链接在下载前尝试获得真实标题、发布时间和博主。
- 查询超时、登录失效、作品删除或平台限制时保留已知数据，记录具体缺失项及原因；不以无结果清空可信旧值。
- 带稳定作品 ID 的历史记录可以按 ID 核对。只有标题的记录先产生候选，需结合博主、完整标题及平台详情验证。
- 截断标题、相似标题、多候选及跨平台同名不能自动判为同一个作品；在页面中进入“待核实/冲突”。
- 网页允许人工补充或纠正标题、平台链接、作品 ID 和发布时间；人工确认标注来源为人工核对，并保留此前值与来源。
- 编辑的平台链接须为匹配平台的 HTTP(S) 作品链接；可解析身份时校验作品 ID 一致，冲突保留核对状态。
- 请求限速、失败退避、查询缓存和断点续查；补齐任务仅查作品信息，不自动下载或转写。

## 9. 下载流程的融合

```text
手动链接 / 监控作品
  → 解析平台、作品身份及元数据
  → 复用既有目录或分配新目录
  → 下载并验证媒体
  → 记录实际下载完成时间与归档索引
  → 自动写作品信息 CSV/JSON/Markdown 与合集清单
  → 原有转写、抽帧、AI 笔记流程
```

- 使用统一归档服务，视频和图文走同一保存规则。
- 现有下载器保留兼容的调用接口；增加下载结果凭据，区分真实下载、既有文件复用和失败。
- 项目自研批量下载工具接入同一服务，避免绕过自动信息记录；第三方工具源码不修改。
- 下载成功信息独立持久化，后续转写或笔记失败仍可查看已经下载的媒体和时间。
- 信息文件使用临时文件与原子替换；同一合集的重建跨进程串行，从索引查询完整集合，避免并发下载相互覆盖清单。
- 数据库先保存可恢复的同步意图，再生成文件。写文件失败记录为归档同步失败，提供单独重试；重试信息文件不重新下载媒体。
- 服务重启可继续待同步的信息写入；待补信息与同步失败在页面中可见。
- 用户修改元数据或归类后自动同步信息文件；既有媒体目录保持稳定，分类变动体现在索引与清单。

## 10. 网页与 API

### 网页

- 导航增加“本地归档”：作品标题、博主、平台、发布时间、下载完成时间、原链接、本地位置、核对状态。
- 支持平台、博主、分组、关键字、时间范围、核对状态筛选；时间筛选明确选择“发布时间”或“下载时间”。
- 缺失时间明确展示未知；时间排序对未知值有稳定位置。
- 支持单作品信息 CSV、当前筛选合集 CSV、补齐信息、人工修正和同步重试。
- 历史索引任务展示进度与已核实/待核实/冲突/失败数量；重复扫描不产生重复条目。
- 现有作品详情增加归档信息区，列表增加下载完成时间；与“本地归档”使用相同后端数据。
- 设置页面展示已生效的默认规则、北京时间与允许根目录，刷新及服务重启后保持规则。

### API 契约草案

沿用 `/api/v1` 和现有 Bearer 认证，更新 OpenAPI、Pydantic 与 TypeScript 类型：

| 路由 | 功能 |
|---|---|
| `GET /archive` | 分页查询及筛选归档记录 |
| `GET /archive/policy` | 获取当前归档规则和允许根目录 |
| `GET /archive/export.csv` | 导出全部符合筛选条件的记录 |
| `GET /archive/{id}` | 归档详情、媒体清单和来源 |
| `GET /archive/{id}/info.csv` | 单作品信息 CSV |
| `POST /archive/scan` | 对指定允许根及相对子目录建立历史索引，返回独立任务 ID |
| `GET /archive/jobs/{job_id}` | 扫描与元数据补齐任务进度 |
| `POST /archive/{id}/refresh` | 查询该作品平台元数据并更新本地信息 |
| `PATCH /archive/{id}/metadata` | 人工修正信息并记录来源 |
| `POST /archive/{id}/sync` | 单独重试作品信息及合集文件同步 |
| `GET /archive/{id}/files/{file_id}` | 访问该归档下已登记且通过根目录校验的媒体文件 |

静态路径与任务路径需优先于动态 ID 路径声明；补齐、扫描与同步执行不占用媒体下载队列。

## 11. 历史母库与原合集的实施要求

先处理用户指定的：

```text
健身/谭成义-b站/「用户521903482」的全部投稿视频/
健身/谭成义-b站/合集_2026-04-25_16-14_哔哩哔哩/合集清单.csv
```

- 首次运行先输出扫描与匹配报告，备份将修改的 CSV/元数据，并使用 SQLite 在线备份方式备份活动库。
- 读取现有单作品 CSV、总表、合集与已有平台列表作为候选信息；针对稳定 ID 查询平台信息。
- 为每个作品目录生成完整字段的 `作品信息.csv`，同时建立网页索引；未知值保持空值和核对状态。
- 总表按作品身份与实际媒体清单重建；原有人工合集按照已有成员更新。
- 只新增或更新信息文件和索引，不重命名、移动、删除、复制或重下载现有媒体。
- 历史真实下载时间无法从可信日志或凭据恢复时标为未知，不能用本次扫描时间补齐。
- 输出修改、未匹配、冲突及查询失败报告，明确哪些信息尚未核实；继续补齐时支持断点恢复。

## 12. 验收标准

1. 从手动入口或监控入口下载一个新作品后，无需额外操作即可生成作品信息 CSV、JSON、Markdown、博主合集和总清单。
2. 新作品目录含已核实精度的发布时间、平台、标题和稳定作品 ID；同名标题不同作品不会覆盖。
3. 网页与文件展示同一平台、原链接、发布时间和下载完成时间，时区统一为北京时间。
4. 下载失败或仅复用媒体不会制造新下载时间；转写失败后已下载信息仍可保留和导出。
5. 字符清洗、长路径、CSV 引号换行、公式型标题、时区跨日、未知时间都按约定处理。
6. 多作品并发归档与中断后重试不会漏合集行或生成重复归档记录；失败可恢复。
7. 历史素材全部建立可追踪的信息记录；媒体路径、文件数、大小与内容在整理前后保持一致。已有真实信息保留，缺失信息有明确状态。
8. 指定旧合集补齐相同成员的信息；筛选导出覆盖全部匹配记录，包括超过一页的数据。
9. 历史扫描不产生媒体下载任务；归档文件访问拒绝越界路径、非法根和指向根外的目录联接。
10. 迁移在现有数据库副本及空库可重复运行；现有下载、作品详情、转写与笔记功能通过必要回归检查。

实现时使用隔离临时数据库及测试目录做后端契约、迁移、失败恢复和归档集成检查，并完成前端类型检查与构建。真实母库操作使用备份和前后对比报告，不把生产库作为测试库。

## 13. GitHub 交付与长期规则

- 设计通过后拆解实施计划：数据与元数据契约 → 自动下载归档 → 历史索引与回填 → 网页/API → 实际验收与发布。
- 更新 README、OpenAPI、归档使用文档及项目级说明，把自动保存信息、时区、目录和历史不移动规则写成长期约定。
- 精确提交本功能的代码、必要测试、设计与说明文档；保留工作区其他已有修改，避免整目录提交。
- 完善相关数据目录忽略规则；数据库、Cookie、`.env`、本机绝对路径映射、媒体、真实作品清单、运行日志与备份留在本机。
- 发布前检查提交差异、GitHub 远端分支及仓库访问权限；不强推。用户已经明确授权最终推送，无需再次询问是否推送。
- 部署到现有本机服务并确认新入口可访问；向用户提供 GitHub 提交链接、归档页面地址、历史回填结果及仍待核实的条目数量。

## 14. 审阅结论

已确认的三项产品选择已全部纳入。其余采用上述默认规则；此规格没有把未知历史时间解释为已补齐，也没有把历史索引加入自动下载队列。

下一步为用户审阅实施计划；用户已确认本设计与产品选择，收到计划认可或修改意见后进入开发。GitHub 推送在功能实现并完成必要验收之后执行。
